# 협업 예시

작업에 필요한 부분만 선택한다. 아래 역할을 모두 동시에 실행할 필요는 없다. 역할은 [roles.md](roles.md), 실행·검토 절차는 [collaboration.md](collaboration.md), 모델 선택은 [models.md](models.md)를 따른다. 각 예시의 작성자는 검토 의견을 받아 자기 소유 산출물을 수정한다.

## 1. 자료 조사와 근거 있는 보고서

- 입력: 조사 질문, 대상 기간, 독자와 원하는 결론의 범위.
- 교환: `researcher`가 출처·날짜·주장·불확실성을 정리하고 `evidence_reviewer`에게 근거가 약한 주장과 상충 자료를 직접 보낸다. 검토자는 출처가 실제로 뒷받침하는 범위를 알려준다.
- 검토·수정: 조사자가 과장된 주장을 줄이고 누락된 근거를 보완한다. 총괄이 핵심 주장과 최신 출처를 대조한다.
- 완료 산출물: 질문에 답하는 보고서, 직접 출처 링크, 남은 불확실성.

## 2. 사업 대안과 재무 시나리오 비교

- 입력: 사업 목표, 비용·매출 자료, 비교 대안과 의사결정 기간.
- 교환: `business_analyst`와 `financial_modeler`가 기간·통화·단위·가정을 직접 맞춘다. 파일 작업이 필요하면 확정된 계산 구조를 `spreadsheet_modeler`에게 전달하고 스프레드시트 소유자를 한 명으로 정한다.
- 검토·수정: 분석가가 가정의 사업상 타당성을, 재무 담당자가 계산·민감도를 확인한다. 모델 소유자가 지적을 반영하고 합계·수식·대표 시나리오를 재계산한다.
- 완료 산출물: 가정과 계산이 확인된 비교표 또는 모델, 조건별 결과와 선택 근거.

## 3. 보고서와 발표 자료 제작

- 입력: 독자, 발표 목적, 원자료, 분량·형식과 시각 기준.
- 교환: `document_producer`가 핵심 내용과 표를 정리하고 `presentation_designer`와 메시지 순서·수치·차트 표현을 맞춘다. 문서와 슬라이드의 소유자는 별도로 둔다.
- 검토·수정: 서로 수치·용어 일치를 확인하고 각 소유자가 수정한다. 근거가 중요한 주장에는 `evidence_reviewer`를 붙인다. 관련 산출물 스킬에 따라 렌더링해 페이지 넘침·잘림·가독성을 확인한다.
- 완료 산출물: 검증된 보고서와 발표 자료, 필요한 경우 발표 노트.

## 4. 창작물과 현지화

- 입력: 대상 독자·지역, 매체, 주제, 톤, 분량과 반드시 유지할 표현.
- 교환: `creative_writer`가 원고와 표현 의도를 `localization_editor`에게 전달한다. 현지화 담당자는 문화적 맥락·말투·중의성을 질문하고 대체 문구를 제안한다.
- 검토·수정: 작성자와 현지화 담당자가 의미 보존·자연스러움의 충돌을 구체적인 문장으로 비교한다. 각 버전의 소유자가 수정하고 용어·누락·분량을 확인한다.
- 완료 산출물: 원본과 대상 언어·지역에 맞는 최종본, 필요한 용어표와 표현 결정.

## 5. 교육 과정과 평가 설계

- 입력: 학습자 수준, 목표 역량, 수업 시간과 활용할 자료.
- 교환: `learning_designer`가 목표·활동·평가 초안을 분야 전문가에게 보낸다. 분야 전문가가 없다면 필요한 전문 범위와 검증 기준을 정한 임시 역할을 만든다. 전문가는 오개념·선수 지식·난도를 지적한다.
- 검토·수정: 설계자가 설명·실습 순서·문항을 수정한다. 전문가가 정답 근거를 확인하고 총괄이 각 평가가 학습 목표를 실제로 측정하는지 대조한다.
- 완료 산출물: 시간 배분이 있는 강의안, 실습, 평가 문항과 해설.

## 6. 업무 운영과 반복 작업 자동화

- 입력: 현재 업무 흐름, 예시 파일, 예외 상황, 허용된 시스템과 변경 범위.
- 교환: `operations_designer`가 입력·출력·예외 처리 규칙을 정리해 `automation_engineer`에게 전달한다. 실제 앱 조작이 필요하면 `app_operator`와 필드·UI 상태·작업 순서를 맞추고 공유 세션의 조작 담당자를 한 명으로 정한다.
- 검토·수정: 개발 담당자가 샘플과 예외 사례로 흐름을 검증하고 운영 담당자가 결과를 확인한다. 발견된 누락·중복 처리를 수정하고 영향받는 사례를 다시 실행한다.
- 완료 산출물: 확인된 자동화 또는 운영 절차, 실행 방법과 예외 처리 안내. 실제 시스템 변경은 기존 사용자 권한 범위에서 수행한다.

## 7. 웹 개발과 사용자 흐름 검증

- 입력: 사용자 흐름, 수용 조건, 기존 프로젝트와 디자인·접근성 기준.
- 교환: `architect`가 데이터·API 계약과 통합 순서를 정한다. 확정된 계약을 바탕으로 `frontend_developer`와 `backend_developer`가 독립 구현하고 계약 변경을 상대와 총괄에게 직접 알린다. 공유 파일은 한 명이 수정한다.
- 검토·수정: 통합 가능한 결과가 나오면 `qa_engineer`가 사용자 시나리오를 검증한다. 필요할 때 `accessibility_auditor`가 구체적인 문제를 담당자에게 보낸다. 담당자는 수정 후 관련 동작을 재검증한다.
- 완료 산출물: 통합된 기능, 실제 검증 결과와 남은 문제. Sites 작업이면 이 프론트·백엔드 위임 예시 대신 사이트 소유 에이전트가 `sites_builder`를 맡고, 하위 전문가는 한정된 자산·조사 결과만 반환한다.

## 8. 스킬 또는 플러그인 제작

- 입력: 해결할 반복 작업, 사용 예시, 대상 환경, 기존 스킬·플러그인과 필요한 도구.
- 교환: `skill_author`가 트리거·작업 순서·예외를 정리한다. 플러그인 요청이면 `plugin_developer`와 스킬·도구·매니페스트 경계를 합의하고 파일 소유권을 나눈다. 스킬만 요청했다면 플러그인 역할은 생략한다.
- 검토·수정: 작성자가 적용되는 제작 스킬을 따라 구현한다. `evidence_reviewer` 또는 독립 검토자가 설명된 기능·권한·도구 인수가 실제 환경과 맞는지 확인하고, 작성자가 불일치를 수정한다. 필요한 구조 검증과 대표 사용 시나리오를 확인한다.
- 완료 산출물: 요청 범위의 스킬 또는 플러그인, 검증 결과, 설치·연결이 필요한 경우 실제 적용 상태와 남은 단계.
