# 전문가 협업 프로토콜

총괄은 작업을 나누고, 전문가들은 필요한 근거와 산출물을 직접 교환한다. 도구·권한·동시 실행 한도는 현재 환경의 실제 명세를 따른다. 역할과 모델은 별도로 선택하며 모델 정책은 [models.md](models.md)를 따른다.

## 배정과 의존성

각 배정에 아래 항목을 짧게 포함한다. 독립 작업이면 불필요한 형식을 늘리지 않는다.

- 목표와 완료 기준, 역할의 전문 범위
- 입력 자료와 선행 결과, 확정된 계약과 아직 확인할 가정
- 출력 형식·위치, 수정할 파일·산출물·UI 자원의 단일 소유자
- 협업 상대의 실제 에이전트 경로, 교환할 정보와 시점
- 검증 방법, 막힘·계약 변경을 총괄에게 보고할 조건

카탈로그에 맞는 역할이 없으면 위 항목으로 임시 역할을 정의한다. 직함은 도구나 계정 권한을 추가하지 않는다. 역할 지침에 읽기 전용이라고 적더라도 실제 샌드박스가 적용되지 않았다면 강제된 격리라고 표현하지 않는다.

필요한 선행 결과가 준비된 뒤 후속 작업을 시작한다. 다만 확정된 인터페이스·단위·독자·형식만으로 진행할 수 있는 부분은 병렬로 배정한다. 가정에 의존하는 작업은 가정과 재작업 가능 범위를 적는다. 검토자를 미리 만들어 초안이 나오기만 기다리게 하지 않는다. 독립적으로 검증 기준이나 출처를 조사할 일이 있을 때만 먼저 배정한다.

## 직접 교환과 도구 의미

생성 결과의 에이전트 ID 또는 실제 경로를 협업 상대에게 전달한다. 다른 하위 트리의 상대를 지정할 때는 전체 경로를 사용한다. 경로를 추측하지 않는다. 상대가 실행 중인지 불명확하고 재개 여부가 중요하면 실제 상태를 확인한다.

| 도구 | 사용할 때와 주의점 |
|---|---|
| `collaboration.spawn_agent` | 독립적으로 수행할 구체적 작업을 생성한다. 지원되는 인수와 모델 설정은 실제 명세를 확인한다. |
| `collaboration.send_message` | 질문·근거·초안·변경 정보를 동료에게 직접 전달한다. idle 에이전트를 재실행하지 않는다. |
| `collaboration.followup_task` | idle 에이전트에게 검토·수정을 다시 맡겨 실행하거나, 실행 중인 에이전트에 후속 작업을 전달한다. |
| `collaboration.list_agents` | 실제 경로·상태를 확인한다. 상태 확인 자체를 목적으로 반복 조회하지 않는다. |
| `collaboration.wait_agent` | 업데이트 도착을 기다린다. 반환값은 업데이트 요약이며 결과 본문을 읽었다는 뜻은 아니다. 전달된 메시지·최종 보고를 확인한다. |
| `collaboration.interrupt_agent` | 현재 턴을 중단해야 할 때 사용한다. 변경 되돌리기·에이전트 제거·슬롯 해제를 보장하지 않는다. |

메시지는 `작업/산출물 버전 → 질문 또는 발견 → 근거·영향 → 요청할 행동` 순서로 간결하게 작성한다. 모든 메시지를 총괄이 중계할 필요는 없다. 범위·소유권·공통 계약의 변경과 해결되지 않은 충돌은 총괄에게 알린다. 정보 교환이 필요 없는 작업에 형식적인 토론을 만들지 않는다.

직접 메시지 도구가 없다면 총괄이 출처·버전을 보존해 내용을 중계한다. 생성 도구도 없으면 현재 에이전트가 역할별 관점으로 순차 수행하고, 실제 병렬 실행이나 전문가 간 대화가 있었다고 주장하지 않는다.

## 자원 소유권과 인계

같은 파일·문서·시트·슬라이드 묶음 또는 상태가 공유되는 브라우저 탭·UI 세션은 한 시점에 한 명만 변경한다. 필요한 경우 자원을 분리해 각자 초안을 만들고 통합 담당자가 합친다. 검토자는 원칙적으로 의견을 전달하고 소유자가 수정한다. 다른 작업자의 변경을 덮거나 되돌리지 않는다.

소유권은 총괄이 명시적으로 이전한다. 기존 소유자의 수정이 끝났거나 중단된 실제 상태와 진행 중 도구 작업을 확인하고, 최신 산출물·미완료 변경·검증 결과를 인계한다. 메시지 전송이나 중단 요청만으로 자원이 비었다고 가정하지 않는다. 공유 UI를 읽는 작업도 탐색·선택 변경으로 다른 작업에 영향을 주면 조율한다.

## 작성 → 검토 → 수정 → 확인

1. 작성자가 산출물 위치·버전·검증 결과와 확인할 쟁점을 검토자에게 보낸다. 검토자가 idle이면 `followup_task`로 검토를 시작한다.
2. 검토자는 완료 기준에 비춰 확인하고, 구체적인 지적에 위치·근거·영향·수정 방향을 붙여 작성자에게 직접 보낸다. 지적이 없으면 억지로 만들지 않는다.
3. 작성자는 수용한 지적을 수정하거나 근거를 들어 반박한다. 작성자가 idle이면 총괄 또는 후속 배정을 맡은 검토자가 `followup_task`로 수정을 재개한다.
4. 작성자는 변경된 버전과 검증 결과를 알린다. 검토자는 수정된 쟁점과 영향을 받는 부분만 필요한 만큼 다시 확인한다.
5. 총괄이 최신 산출물과 실제 검증 결과를 확인하고 통합한다. 전문가의 성공 보고만으로 완료를 선언하지 않는다.

보통 한 번의 검토와 수정으로 충분하다. 새 근거나 미해결 결함이 있을 때만 반복한다. 의견이 충돌하면 각자가 쟁점·근거·판별 방법을 제시하고, 가능한 테스트·자료 확인으로 해결한다. 남은 선택은 총괄이 사용자 요구·완료 기준·비용을 기준으로 결정한다. 다수결·직함·모델 크기로 결론을 정하지 않는다. 새 근거가 없는 논쟁은 종료하되 중요한 미해결 문제를 숨기거나 완료로 처리하지 않는다.

검증은 산출물에 맞춘다. 예를 들어 코드 실행, 데이터 재계산, 출처와 주장 대조, 문서 렌더링, 슬라이드 가독성 확인, 교육 목표와 평가 문항 대조를 수행한다. 수행하지 못한 검증과 남은 불확실성은 보고한다.

## 실행 한도와 환경 경계

동시 실행 한도에 루트·다른 실행 중 작업이 포함되는지 실제 명세를 확인한다. 루트 포함 4개인 환경에서는 루트가 작업하는 동안 하위 에이전트는 최대 3개다. 한도를 넘어 역할 수만큼 생성하지 않으며, 완료·중단이 슬롯을 해제하는 방식도 추측하지 않는다. 지원되는 상태 조회와 기존 에이전트 재사용을 우선한다.

독립적으로 진행할 일이 없을 때만 기다린다. 사용자와의 소통을 막지 않도록 한 번의 대기는 60초 이하로 제한하고 필요하면 진행 상황을 알린 뒤 다시 기다린다. 상위 지침과 도구의 실제 제한이 우선한다.

`mcp__codex_app__create_thread`는 사용자가 새 작업을 명시적으로 요청했을 때 만드는 별도 사용자 작업이다. 현재 요청의 전문가 하위 작업에는 하위 에이전트 도구를 사용한다. 새 작업 생성으로 팀 실행이나 동시 실행 한도를 우회하지 않는다.

`codex-team`은 실제로 연결된 도구가 있을 때만 그 명세에 맞춰 사용한다. 설치·연결·팀 메시지·모델 지정 기능을 이름만으로 가정하지 않는다. 현재 환경이 지원하지 않는 기능은 제한을 밝히고 총괄 중계나 순차 작업으로 진행한다.
